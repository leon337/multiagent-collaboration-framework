O que já virou ecossistema

Pense em uma estação: o MCF é o centro de controle, o Ledger é o arquivo, o TriView é o painel e o Cloud é a casa de máquinas. O painel já sabe onde cada peça está, e as duas passagens read-only funcionaram no laboratório. Main, staging e as fichas semânticas dos quatro projetos foram reconciliados. A conferência final recuperou 4/4 projetos com HEAD, worktree limpa e referência live exata.

O MCF já possui contratos, schemas, Registry dos quatro projetos, leitura de Capsules, verificação de freshness e dois endpoints GET-only protegidos. O CF-0/CF-1 foi incorporado ao main no PR #153; CF-2 e o Capability Registry foram IMPLEMENTED_AND_VERIFIED_IN_BRANCH no checkpoint e646527f, agora ancestral do closeout do PR #161. O recovery estrutural final pós-sync passou 4/4 no main@2dc4584.

O Cognitive Ledger comprovou a rota final de três operações pelo AppModule, com token próprio, raw bloqueada, 3 auditorias, memória não persistida e nenhuma API paga. O TriView apresenta recovery e capabilities de forma read-only no branch de release. Ledger PR #3, TriView PR #78 e Cloud PR #27 fecharam o sync semântico pós-main. O cliente real do MCF passou 3/3 testes E2E contra o processo Cloud stdio descartável. Ledger e o provider Cloud local permanecem DISCONNECTED/INACTIVE; o G2-A remoto permanece NOT_AUTHORIZED/DISCONNECTED/UNKNOWN/LIVE_REQUIRED, e o G2-B, NOT_AUTHORIZED/DISCONNECTED/BLOCKED/LIVE_REQUIRED.

Portanto, “implementado” não significa automaticamente “conectado”, “autorizado” ou “verificado”. Essa separação impede que um agente trate código existente como permissão operacional.

04 / GUARDRAILS

Regras que não podem quebrar

Estas regras transformam integração em cooperação segura, em vez de dar uma chave mestra a cada agente.

01

Owner por verdade

Registry identifica; cada repo mantém seu contexto; Cloud mantém estado operacional; Ledger mantém memória auditável.

02

Read-only degrada; write fecha

Leitura pode informar stale/offline. Escrita nunca continua por cache, suposição ou evidência histórica.

03

Freshness visível

Repo root, HEAD, worktree e observed_at acompanham a afirmação; snapshot não se fantasia de estado live.

04

Segredo fora do contexto

Tokens ficam em variáveis/secret stores. Capsule, Registry, Ledger, Receipt e TriView guardam apenas referências seguras.

05

Bootstrap independente

O MCF recupera identidade mesmo com Ledger, TriView, provider de IA ou Cloud offline.

06

VPS é outro boundary

Continuidade da VPS segue em frente paralela preservada. Nenhuma evidência local aqui concede acesso ou altera o ambiente.

05 / CUSTO ZERO

IA sem cobrança por API

Custo zero é uma restrição arquitetural: nenhuma rota automática pode cair silenciosamente em provider pago.

R$ 0 chamadas pagas e embeddings nos E2Es Ledger observados

Política operacional

  • ChatGPT pode continuar sendo a interface humana atual, sem exigir chave paga dentro dos serviços.
  • Embeddings pagos ficam estritamente opt-in e desabilitados no caminho padrão.
  • Busca estruturada, leitura repository-native e fallback local continuam disponíveis sem provider externo.
  • Qualquer API gratuita futura deve ficar atrás de adapter neutro, quota explícita e fallback offline.
  • Testes de integração devem provar zero chamadas pagas, não apenas confiar em configuração.
Evidência final MCF → Ledger: o provider mantém 4 tools, mas o MCF allowlista 3. O E2E fez 3 operações, gerou 3 auditorias, bloqueou raw, manteve o fingerprint 953cf4f346240c029c3bcd584d02eed0 e registrou 0 embeddings/0 chamadas pagas.
